1. Problem Statement

The Capella design team audits digital assets and content entirely by hand — clicking through pages one by one to find which images are live, whether those pages are published, whether duplicate assets exist in the DAM, and where testimonials appear across the site.

At tens of thousands of assets, hundreds of pages, and audits that span 1000+ URLs, this is completely unsustainable. Testimonials are especially difficult: stored as both reusable AEM components and hardcoded text, they must be searchable by quote, student name, and program, and audited for freshness and coverage gaps across degree programs.

Additionally, there is no structured intake process for video assets. Internal staff and external vendors submit videos through ad hoc channels, bypassing legal and marketing review, and assets land in the DAM without consistent metadata, tagging, or approval status. This creates legal exposure and brand inconsistency.

Scraper: Playwright (not Cheerio)
Capella's site is JS-rendered — a static HTML fetch returns only navigation, not page body content. This was confirmed by live page inspection. Playwright waits for networkidle before extracting the fully rendered DOM, then pulls /content/dam/ asset references and testimonial components in a single pass per page.

~3–5 seconds per page (JS render + network idle)
101 URLs from the audit doc: ~8–10 minutes total
1000 URLs: ~60–90 minutes — acceptable as a background job
5 concurrent Playwright pages max (heavier than fetch)
Sitemap XML fetched with plain node-fetch (static, no JS needed)
Phase 2: testimonials switch to AEM Query Builder — Playwright retained for asset references

Scale architecture — job queue (required for 1000+ URLs)
Audit jobs run as background tasks. A 1000-URL audit takes 20–40 minutes at safe scraping rates and would time out as a single HTTP request.

User uploads CSV / pastes URLs / imports sitemap URL
        ↓
POST /api/v1/audit → creates AuditJob → enqueues to BullMQ → returns { jobId }
        ↓
Worker processes pages in batches of 5 (Playwright) — writes results to DB
        ↓
UI polls GET /api/v1/audit/:jobId/status → live progress bar
        ↓
Results queryable as they arrive — no waiting for full completion

5. AEM Query Builder API Reference  (Phase 2)

All calls go to GET /bin/querybuilder.json on the AEM author instance via capella-dam-audit-svc.

⚠️  Default limit is 10 hits — always set p.limit explicitly or results will be silently truncated.

Find pages referencing a specific asset
GET /bin/querybuilder.json
  ?path=/content/capella/en  &type=nt:base
  &property=fileReference
  &property.value=/content/dam/capella/images/hero.jpg
  &p.limit=500  &p.hits=selective  &p.guessTotal=true
  &p.properties=path jcr:content/jcr:title jcr:content/cq:lastReplicated

Find all pages ordered by last modified
GET /bin/querybuilder.json
  ?type=cq:Page  &path=/content/capella/en
  &orderby=@jcr:content/cq:lastModified  &orderby.sort=desc
  &p.limit=100  &p.guessTotal=true

Find pages by program tag
GET /bin/querybuilder.json
  ?type=cq:Page  &path=/content/capella/en
  &tagid=programs/masters-degree
  &tagid.property=jcr:content/cq:tags
  &p.limit=200  &p.guessTotal=true

Find all testimonial components
GET /bin/querybuilder.json
  ?path=/content/capella/en  &type=nt:base
  &nodename=testimonial  &p.limit=1000  &p.hits=full

Key Query Builder parameters
Parameter
Purpose
p.limit
Max results. ALWAYS set explicitly — default is 10
p.offset
Pagination start index
p.guessTotal=true
Fast pagination — returns more: true when results exceed limit
p.guessTotal=N
Exact count up to N, then more: true
p.hits=selective
Return only p.properties fields — always prefer over full
p.hits=full
Return all properties — avoid in production
p.properties
Space-separated list: path jcr:content/jcr:title
orderby
Sort property, prefix @ for JCR: @jcr:content/cq:lastModified
orderby.sort
asc or desc
group.p.or=true
OR logic for grouped predicates (default is AND)
1_property, 2_property
Numeric prefix for repeated predicates
tagid
Tag matching — pair with tagid.property=jcr:content/cq:tags

Performance note:
Always use p.guessTotal for large result sets — exact counts require reading the entire result set for access control, which is a significant difference in execution time at scale.

6. Video Intake Architecture

The intake flow is the only place this tool writes to AEM. The video file is uploaded directly to a restricted AEM DAM staging folder and never held in this tool's own storage.

Submitter agrees to legal terms + submits form (public — no AEM credentials)
        ↓
Validation: legal_agreed checkbox must be true — blocks submission if unchecked
        ↓
Tool streams video to AEM via Assets HTTP API — never buffered in memory
  POST /api/assets/capella/intake/pending/{filename}
        ↓
Metadata written: dam:status=pending-review, tags, submitter, legal fields
        ↓
VideoSubmission record created — transcription job enqueued
        ↓
Approvers notified — transcript + chapters available in review view
        ↓
All approvals → MOVE asset to /content/dam/capella/{program}/videos/
Any rejection → notify submitter with reason — allow resubmission

AEM write calls (capella-dam-intake-svc only)
POST /api/assets/capella/intake/pending/{filename}           ← upload
PUT  .../{filename}/jcr:content/metadata                     ← set tags
MOVE /content/dam/capella/intake/pending/{filename}          ← approve
PUT  /api/assets/capella/{program}/videos/{filename}/...     ← status

Transcription pipeline (Whisper API — ~$0.006/min)
ffmpeg extract audio → /tmp/{jobId}.mp3  (deleted in finally block)
        ↓
POST https://api.openai.com/v1/audio/transcriptions
  model: whisper-1  response_format: verbose_json
        ↓
Generate .vtt caption file → upload to AEM alongside video
LLM chapter detection on transcript text → store as JSON metadata

Whisper API: $0.006/min — 10min video ≈ $0.06, 100 videos/month ≈ $6
Temp audio file deleted in finally block — guaranteed even on error
Transcription failure never blocks the approval workflow
Whisper 25MB audio limit ≈ 45 min video — longer videos chunked

Legal agreement
Checkbox required — submission blocked entirely if unchecked (client + server enforced)
Agreement timestamp and IP address recorded on every submission
Optional PDF upload (vendor contracts, talent releases) — stored in tool DB, not AEM
Legal team must approve terms copy before launch — see Open Questions

8. Testimonial Scraping Selectors  (Phase 1)

The Playwright scraper detects testimonials using these CSS/attribute patterns from the fully rendered DOM, in priority order:

#
Selector
Rationale
1
[data-component="testimonial"]
AEM component data attribute — most reliable
2
.cmp-testimonial
AEM Core Components standard class
3
.testimonial  /  .student-quote
Capella custom component classes
4
blockquote + [class*="name"]
Quote element followed by attribution
5
[class*="quote"] + [class*="student"]
Generic quote + student combo

For each match, extract:
quote_text — visible quote string, HTML tags stripped
student_name — text matching “— Name” pattern or nearby .name element
program — text matching known Capella degree strings or nearby .program element
raw_html — full outer HTML of matched element for manual review
9. Non-Goals

Do NOT write to AEM except through the video intake flow — all other operations are read-only
Do NOT host or store video files — upload directly to AEM DAM, never buffer in this tool
Do NOT build a full DAM or video management platform — intake and approval only
Do NOT build a social publishing or scheduling tool
Do NOT replace AEM’s native DAM interface
Do NOT auto-verify whether a testimonial is current — flag for human review only
Do NOT process bulk audits synchronously — all multi-URL jobs must use the job queue
Do NOT publish AEM pages automatically after video approval — asset moves to live DAM only
